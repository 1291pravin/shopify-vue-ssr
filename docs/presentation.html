The problem

Pages arrive empty until JavaScript runs

Every section of the storefront is a Vue component rendered in the browser. Visitors on a mid-range phone wait about 5.5 seconds for any content. AI assistants such as ChatGPT, Claude and Perplexity do not run JavaScript, so they read almost nothing.

Live site, 11 Nov 2026. Lab test: phone emulation, slow 4G, median of 3 runs.

Illustration of the loading order, not measured timings.

Speaker notes. The problem in one sentence: the storefront is built from Vue sections, and every one of them is empty in the HTML that Shopify sends. Content appears only after the JavaScript bundle has downloaded and run. That hurts two audiences. Visitors: in a lab test of the live site, emulating a mid-range phone on slow 4G, first content appeared after about 5.5 seconds on the home page, a product page and a collection page alike. Nothing is painted before Vue has rendered. AI assistants: the crawlers behind ChatGPT, Claude and Perplexity read the raw HTML and, as far as is publicly documented, do not run JavaScript. On our home and product pages the raw HTML holds 59 characters of visible text, no headings, two links and no images. Product pages do carry structured product data, and Google does run JavaScript, so Google search is not affected in the same way. The animation is an illustration of the order of events, not a recording.

Speaker notes. The idea: Shopify cannot run Vue on its servers, so we render the Vue sections ourselves, in advance, and Shopify inserts the result. For anyone who knows Vue, this is the same server render and hydration that Nuxt does, run in the pipeline instead of on a server per request. There is no proxy and no rendering server; the visitor only ever talks to Shopify. Two flows. Flow A runs in GitHub Actions on every deploy and once a night. Code is merged; the theme is built and deployed to Shopify as it is today; then each Vue section is rendered to HTML with the real data from our pages; the HTML is tested to make sure Vue hydrates it cleanly at mobile and desktop widths; and only HTML that passes is saved in Shopify. Flow B runs for every page view. The visitor opens a page and Shopify builds it. For each section Shopify asks one question: is there stored HTML for this section with exactly this data? If yes, the HTML goes straight into the page, the visitor sees content at once, and Vue then hydrates it so the page is interactive. If no, for example because a price changed since the last run, the section arrives empty and Vue renders it in the browser. That dashed path is exactly what every section does today, so the worst case is today’s speed, never a broken page. Both paths end at the same fully interactive page.

Other solutions considered

OptionHow it worksVerdict
Pre-rendered VueVue is rendered after each deploy and the HTML is stored in ShopifyChosen. Keeps our Vue code, needs no server, and a miss behaves exactly like today.
Rewrite sections in LiquidShopify renders the markup; Vue only adds behaviourRejected. Every section template is rebuilt, then maintained twice, in Liquid and in Vue.
Simple Liquid fallback per sectionA plain version is shown first, then Vue replaces itRejected. Two templates per section to keep in step, and AI assistants read the poorer copy.
Rendering proxy in front of ShopifyOur own server renders Vue on every page requestRejected. Shopify does not support proxied storefronts well; adds delay and an outage risk to every page view.
Headless rebuild (Nuxt or Hydrogen)A new storefront built on Shopify’s APIRejected. A full rebuild that gives up the theme editor and most theme apps.

Speaker notes. We looked at five ways to get HTML into the first response. A simple Liquid fallback per section, shown first and then replaced by Vue, is always fresh, but every section then exists twice, the two drift apart, and crawlers that do not run JavaScript only ever read the simpler copy. Rewriting sections in Liquid is what a classic Shopify theme does and it is always fresh, but it means rebuilding every section template and then keeping two versions of each in step. A rendering proxy gives true per-request rendering, but puts our own server between every visitor and Shopify; Shopify does not support that setup well, and if the server is slow or down, the whole shop is. Going headless with Nuxt or Hydrogen is a new storefront project, and we would lose the theme editor and most of the apps that plug into the theme. Pre-rendering is the only option that keeps the Vue code we have, adds no infrastructure, and cannot make things worse: where stored HTML is missing or out of date, the section simply renders in the browser as it does now. It suits this store in particular because the site is small, about 205 pages (65 products, 49 collections, the rest content pages and articles), and content rarely changes.

Speaker notes. Answers to likely questions. Status: the pilot is deployed on a preview theme and working; the live site is untouched. Size: about 205 pages in the sitemap (65 products, 49 collections, the rest content pages and articles), so one run covers the whole site. Freshness: when content changes, that section falls back to today’s behaviour until the next run; the plan is a run after each deploy, a nightly full run, and a short scheduled run in between. Limits: Shopify allows 20 stored sections per page and our pages have 15 to 20, so content sections get priority over drawers and loaders; each stored section can hold about 65 KB of HTML. Privacy: cart and login details are never stored; they are added in the browser. Measurement: the 5.5 seconds is a lab test of the live site, not real-visitor data; the same test on the pilot theme has not been run yet.
